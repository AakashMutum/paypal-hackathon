# 1. PROJECT OVERVIEW

## 1.1 What is Trustora?

Trustora is an AI-assisted payment security and merchant verification system designed to protect customers from potentially fraudulent or misleading online checkout experiences.

The main problem it addresses is that customers may believe they are paying a legitimate brand or merchant on a storefront, but the actual merchant receiving the PayPal payment could be a different entity.

Trustora introduces an additional security layer between the customer's checkout experience and payment execution.

Instead of blindly proceeding with payment, the system evaluates the merchant, website, pricing and technical indicators before allowing a payment to proceed.

## 1.2 Main objective

The primary objective is:

**Verify that the merchant presented to the customer matches the actual merchant receiving the PayPal payment, while identifying suspicious checkout conditions before payment capture.**

The system should:

1. Analyze the merchant and storefront.
2. Evaluate website and domain reputation.
3. Check merchant identity consistency.
4. Detect suspicious pricing and unusual discounts.
5. Evaluate SSL and technical security indicators.
6. Calculate an overall risk score.
7. Produce a payment decision.
8. Enforce that decision through the backend.
9. Integrate with PayPal for order creation and payment capture.
10. Maintain an auditable record of checkout and payment decisions.

## 1.3 Main differentiator

The most important differentiator is **PayPal Payee Identity Verification**.

For example:

A customer visits a storefront claiming to sell products from Brand A.

The checkout interface displays Brand A as the merchant.

However, when the PayPal order is retrieved, its actual payee information identifies Merchant B.

Trustora should detect this inconsistency and prevent automatic payment capture.

This is more than a normal fraud score. It connects the storefront's claimed merchant identity with the actual payment recipient.

# 4. RISK ASSESSMENT MODEL

The PRD specifies four primary risk components.

| Risk component | Weight |
|---|---:|
| Domain age and reputation | 30% |
| Merchant identity consistency | 40% |
| Pricing anomalies | 20% |
| SSL and technical indicators | 10% |
| **Total** | **100%** |

The overall risk score is between 0 and 100.

## 4.1 Decision thresholds

| Score | Decision | Expected behavior |
|---|---|---|
| 0–39 | ALLOW | Eligible to proceed after required checks |
| 40–74 | WARN | Customer acknowledgement required through the approved warning flow |
| 75–100 | PAUSE | Prevent automatic payment capture |

The backend must enforce the final payment decision.

The frontend must never be able to override a PAUSE decision by submitting its own ALLOW value.

An LLM may assist with analysis, but its output is probabilistic and must not be treated as proof of fraud.

High-risk decisions should have deterministic supporting evidence.

**Important PRD clarification:** The discount anomaly threshold is described inconsistently in different parts of the PRD (>70% versus >80% below baseline). This must be clarified with the team rather than silently choosing one threshold.

- Reaffirms `chk_payment_decision`.
- Permits only `ALLOW`, `WARN`, and `PAUSE`.
- Uses a new sequential migration rather than modifying an already-applied migration.

This is an important database maintenance decision. Do not rewrite migration 001.

# 6. MILESTONE 3 — DATABASE INTEGRATION AND TEST FIXES

Status: Completed.

Two important bugs were discovered and fixed.

## 6.1 Bug A — Payment decision CHECK constraint

Problem:

PostgreSQL was returning:

`value too long for type character varying(10)`

instead of the expected named CHECK constraint violation.

Root cause:

The decision column was too narrow for the invalid test value.

Solution:

Created migration 002 to widen the column to `VARCHAR(20)` and re-establish the decision constraint.

Verification:

The integration test now correctly verifies the named `chk_payment_decision` constraint.

## 6.2 Bug B — Health test environment isolation

Problem:

The health test expected:

`database.status = not_configured`

But the actual result was:

`database.status = healthy`

Root cause:

The root `.env` contained a valid PostgreSQL connection URL.

`dotenv.config()` loaded that configuration into the application, so the health check connected to the actual development database.

Solution:

Modified:

`apps/api/src/config/env.ts`

Added:

`setDatabaseUrl(url)`

This allows the test to temporarily override the configured database URL.

Modified:

`apps/api/test/health.test.ts`

The test now:

1. Saves the original database URL.
2. Temporarily clears the database URL.
3. Resets the cached database pool.
4. Checks the not-configured health response.
5. Restores the original URL using `try/finally`.

This preserves the developer's `.env` configuration and avoids deleting or modifying local credentials.

# 12. EXPECTED END-TO-END PAYMENT FLOW

The completed backend should follow this sequence:

1. Customer initiates checkout.
2. Backend receives the checkout request.
3. Backend identifies the merchant using trusted application data.
4. Risk assessment runs.
5. Risk score is calculated.
6. Backend records ALLOW, WARN or PAUSE.
7. If PAUSE, the payment cannot proceed to capture.
8. If ALLOW or an appropriately acknowledged WARN, the backend creates a PayPal order.
9. Customer approves the PayPal order through the appropriate frontend flow.
10. Backend retrieves the approved order from PayPal.
11. Backend inspects actual PayPal payee information.
12. Backend compares actual and expected merchant identity.
13. Backend rechecks the payment decision and required conditions.
14. If the merchant is verified and all conditions are satisfied, the backend captures the order.
15. Backend records the final payment state and audit evidence.
16. Frontend displays the verified result.

The backend must remain the final authority for payment capture.
