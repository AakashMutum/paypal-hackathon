# Latency

Generated by `npm run measure:latency -- --write` on 2026-11-04. Re-run it to refresh the numbers; do not edit the table by hand.

## What was measured

- 10 sequential `POST /api/scan` requests per store, to http://localhost:3100, timed from sending the request to reading the whole response body.
- The first request to each store is reported separately. The very first request of the run is the cold start of the API process; if the API was already warm, it is not.
- The three stores are invented (`.example` domains). With `SIGNALS_MODE=auto` they are answered from recorded signals, so the scan does not touch the network for them. Live signals for other sites were not measured here.
- Modes reported by `/health` during the run: `{"paypal":"simulated","store":"memory","signals":"auto","llm":"none","llmProvider":"openai-compatible","llmModel":"gpt-4o-mini","llmModels":{"fast":["gpt-4o-mini"],"strong":["gpt-4o-mini"]},"llmKeySource":"none","memory":"file","memoryPersistent":true,"embeddings":"local-hash:v1","memorySize":28,"memoryLocation":"D:\\Hackathon\\Paypal-Hackathon\\paypal-hackathon\\.cache\\trustora-memory.json","auditEncryption":"disabled"}`. The model time budget (`AGENT_MODEL_BUDGET_MS`, default 1200) is read by the API process and is not reported by `/health`; use `--note` to record a non-default value.
- Machine: Intel(R) Core(TM) 5 120U (12 logical cores), 15.6 GiB RAM, win32 10.0.26300, Node v22.21.0. The client and the API ran on the same machine, so there is no network latency in these numbers.

## What this does and does not show

- It measures the API as it was configured for the run. If the language model was off or answering from recordings, these numbers say nothing about a live model: a live model adds its own network time, which is bounded by `AGENT_MODEL_BUDGET_MS` (default 1200 ms) but not measured here unless the modes above say `"llm":"live"`.
- The previous local measurement reported by the team, 5 live scans of 1733, 1848, 1887, 2055 and 3740 ms (the cold first request was 3.74 s), was not reproduced by this script.
- The run is small and on one machine. It is not a service-level measurement.

## Experiments run on the same machine

These were run by hand with the scripts in `scripts/latency-experiments/`. They are small and are not regenerated by `--write`.

### Does the startup warm-up help?

`apps/api/src/services/warmup.service.ts` runs after the server starts listening, without blocking it. It checks the database connection, reads the memory store and runs one investigation of the invented genuine demo store, only when that store is answered from recorded signals (never in `SIGNALS_MODE=live`). Nothing is stored and no real site is contacted. Set `WARMUP=off` to disable it. It is also off when `NODE_ENV=test`.

`node scripts/latency-experiments/warmup-trial.mjs 6` starts a fresh API process 6 times with the warm-up off and 6 times with it on, waits 2.5 seconds, then times the first `POST /api/scan` (the store rotates between trials):

| Warm-up | First request after start (ms) | Median |
| --- | --- | --- |
| off | 160, 84, 95, 77, 79, 96 | 95 |
| on | 41, 43, 58, 41, 46, 63 | 46 |

The warm-up itself took 41 to 64 ms. In this configuration (no model, recorded signals) it roughly halves the first request, an absolute saving of about 50 ms. It does not change the order of magnitude. With a live model or live signals, the first connection to those services is not primed by it.

### Does the model time budget bound a slow model?

`AGENT_MODEL_BUDGET_MS` did not exist before this change; it was added with a default of 1200. It is the total time all model calls of one investigation may use. After it, remaining model steps are skipped and the deterministic output is used; the result records `stats.modelBudget` and the provenance shows `modelBudget.exhausted`.

To test this without a model key, `scripts/latency-experiments/fake-llm.mjs` is a local stand-in for an OpenAI-compatible provider that answers every call after 700 ms with an answer that fits no schema. **This is not a real model and says nothing about Gemini's latency.** The API ran with `LLM_MODE=live` pointing at it, 6 scans per store (first plus 5 warm), warm-up off:

| Store | Budget off (`AGENT_MODEL_BUDGET_MS=0`), warm median (ms) | Budget 1200, warm median (ms) |
| --- | --- | --- |
| Harborline Outfitters (genuine, no model call) | 159 | 168 |
| Bargain Barn Outlet (discount) | 4450 | 1320 |
| Harborlyne Outfitters Sale (impersonator) | 2916 | 1297 |

Warm requests under 2000 ms: 5 of 15 with the budget off, 15 of 15 with 1200. So the budget does bound the model portion of a scan to about 1.2 seconds on top of the deterministic work. The decision and score do not depend on it (`packages/agent/tests/modelBudget.test.ts`). What it costs: when a real model is slower than the budget, its answers (follow-up checks, name comparison, plain-language explanation) are replaced by the deterministic versions for that scan.

### What is and is not met

- Met in this measurement: with recorded signals and no model, every request, including the first, was well under 2 seconds. With a simulated 700 ms model and the 1200 ms budget, every warm request was under 2 seconds.
- Not measured: a live scan with a real model and live signals on this code. The team's earlier local numbers (1733, 1848, 1887, 2055, 3740 ms) were not reproduced, and I had no model key. Whether a real model's calls fit in the budget, and so how often a live scan falls back to the deterministic explanation, is unknown.
- Not measured: the hosted instance.

## The hosted instance

The free Render instance sleeps after about 15 minutes without traffic. The first request after that wakes the service and is cold: it can take far longer than 2 seconds (the smoke script allows up to about 70 seconds). Judges who open the hosted demo after it has been idle should expect a slow first request; later requests are warm. No hosted measurement exists yet because nothing is deployed. Run `BASE_URL=<hosted url> npm run measure:latency -- --write` after deploying and read the first row separately.
